# L3 · Memory pressure

Use a dedicated disposable cgroup-v2 container. Each control run touches 16 MiB. The failure run attempts at most 128 MiB and Docker caps it at 64 MiB with swap disabled. No cloud resources are needed.

```sh
LAB=01-architecture-A01-to-A20/A01-computer-systems-and-os/labs
docker run --rm --network none --memory 64m --memory-swap 64m -v "$PWD/$LAB:/lab:ro" python:3.12-slim python /lab/memory_pressure.py
id=$(docker create --network none --memory 64m --memory-swap 64m -v "$PWD/$LAB:/lab:ro" python:3.12-slim python /lab/memory_pressure.py --break)
docker start "$id"
docker wait "$id"
docker logs "$id"
docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}' "$id"
docker rm "$id"
```

1. Predict the change in `memory.current` after each touched buffer. Its value also includes other cgroup charges and can fluctuate.
2. Compare the last logged sample, status, and OOM flag. Expect a kernel kill and typically exit 137 with `OOMKilled=true`. If this differs, record Docker's actual status and check the memory controller and swap settings. The script rejects absent or unexpected limits.
3. Repair by reducing the live set as in the normal control. Extend by varying the allowed cap between 48 and 80 MiB or dropping each buffer after measuring it.
4. Record the observed cap, samples, terminal status and final cleanup. The cap can be exceeded while the node still has free memory, because the limit applies at the workload boundary.
